# Laporan uji keamanan, beban, dan chaos (Poin 14), 3 November 2026

Uji ini dijalankan sekali di stack dev, dalam urutan keamanan → beban → chaos, memakai alat di `tests/` (cara pakai: [README.md](README.md)). Data mentah ada di `tests/results/` mesin dev. Folder itu tidak di-commit; nama folder dicantumkan per bagian.

> **Uji ulang setelah perbaikan (3 Nov malam):** lihat [bagian 9](#9-setelah-perbaikan-3-nov-malam). Ringkasnya, T1 dan T2 diperbaiki untuk ukuran yang diuji: 100% pesan sampai lewat Realtime sampai 400 penerima dan pada spike 0 → 300, dengan p95 ≤ 26 ms. Bottleneck pertama yang baru muncul di ±450–500 penerima satu room: batas tenant 10.000 event/dtk, dan hampir bersamaan konvoi kunci baris `chat_rooms` di `send_message` yang menghabiskan pool PostgREST.

> **Uji ulang setelah perbaikan T17–T19 (4 Nov):** lihat [bagian 10](#10-setelah-perbaikan-t17t19-4-nov). Konvoi kunci `chat_rooms` (T17) hilang: 0 lock wait sampai 800 penerima, pratinjau room tertinggal ≤ 0,7 dtk. Isi celah dari horizon (T18) mencapai 100% eventual setelah crash Realtime dan pada 500 penerima dengan 24% event dibuang batas tenant. Lonjakan sambung ulang (T19) tersebar ±15 dtk, `rest` ≤ 22%. Penyebab sebenarnya runtuhnya `rest` di 500–600 penerima ternyata **T20**: runtime GHC PostgREST memakai 28 capability (jumlah core host) di dalam kuota 1 vCPU. Dengan `GHCRTS=-N1`, 600 penerima bersih (0% error, `send_message` p95 48 ms); bottleneck berikutnya CPU db pada 800.

## 1. Ringkasan

**Bottleneck pertama: pengiriman pesan Realtime ke banyak penerima, bukan API atau database.**

- Room saham ramai dengan sekitar 6–7 pesan/detik bisa diikuti 100 nasabah tanpa masalah: 100% pesan sampai, latensi p95 0,56 dtk.
- Mulai sekitar 150–200 penerima, total kiriman melewati **batas tenant Realtime 1.000 event/detik** (`TENANT_MAX_EVENTS_PER_SECOND`). Realtime lalu **membuang pesan diam-diam** (log `MessagePerSecondRateLimitReached`). Yang sampai ke penerima tinggal:

  | Penerima | Pesan sampai |
  |---|---|
  | 200 | ±60% |
  | 300 | 27–36% |
  | 400 | 17% |

  Batas ini berlaku untuk **seluruh tenant**: semua room, termasuk chat CS di web CS, ikut kehilangan event.
- Dengan batas dinaikkan (overlay opt-in), 200 penerima kembali 100%. Pada 400 penerima, antrean `postgres_changes` di Postgres tertinggal: latensi p50 12 dtk dan p95 22 dtk. Itu bottleneck berikutnya.
- API REST, RPC, exchange auth-bridge, dan PgBouncer tetap ringan sampai 400 VU (±60 request/detik): p95 di bawah 25 ms, error 0%, tidak ada antrean di pool.

**Keamanan:**

- Dari 1.042 probe otorisasi, tidak ada kebocoran data antar-nasabah, antar-peran, maupun dari anon.
- Satu temuan: anggota room bisa mengirim **event sinyal server palsu** (`message_hidden`, `room_state`, `reaction`) lewat broadcast ke kanal `room:<id>`. Siapa pun bisa menjadi anggota room saham.
- Konfigurasi edge produksi lulus 84 cek statis dan 39 cek dinamis (TLS, header, path publik, 413, rate limit, batas WebSocket).
- Dependensi kode kita bersih: govulncheck 0, npm prod 0, pubspec 0. Image dasar cs-console dan classifier membawa CVE OS (1 CRITICAL, 5 HIGH) yang praktis tidak terjangkau.

**Chaos:** semua 9 eksperimen pulih sendiri tanpa tindakan manual.

| Gangguan | Perilaku | Waktu pulih |
|---|---|---|
| Crash layanan Go/PostgREST/PgBouncer/Realtime | Pulih lewat restart policy | 5–8 dtk |
| Restart Postgres | REST tidak tersedia | ±17 dtk |
| Classifier mati | Upload gambar **fail closed** (503) | — |
| Valkey mati | auth-bridge **fail open** ke limiter lokal per instance, batas per IP tetap berlaku | — |

- Tidak ada pesan yang hilang dari DB: semua `send_message` yang dijawab 200 tersimpan.
- Alert Kesehatan sistem muncul lalu selesai dengan benar.

## 2. Lingkungan uji

- **Mesin:** Windows 11 dengan Docker Desktop (WSL2), 28 CPU logis dan 31 GiB untuk Docker. Stack dev `olt-social` lengkap memakai batas CPU/memori dari `docker/compose.yml`, sama dengan produksi:

  | Service | CPU | Memori |
  |---|---|---|
  | db | 2 | 2 GiB |
  | rest | 1 | 512 MiB |
  | realtime | 2 | 1 GiB |
  | kong | 2 | — |
  | pgbouncer | 0,5 | — |
  | auth-bridge | 0,5 | — |
  | traefik | 1 | — |

  Container proyek lain di mesin ini idle.
- **Generator beban:** k6 2.2.0 di image `olt-social/testkit` di mesin yang sama. Jalurnya `testkit → Kong (IP edge) → layanan`. Traefik dilewati agar batas per IP edge tidak membatasi satu IP generator. Batas edge diuji terpisah (3.2).
- **Batas aplikasi tidak diubah.** Rate limit DB per user, per IP auth-bridge, dan per key tetap aktif. Setiap VU punya IP sintetis sendiri lewat `X-Forwarded-For`, yang hanya dipercaya Kong dari subnet edge.
- **Satu pengecualian, ditandai jelas (4.3):** langkah kapasitas "overlay" menaikkan `TENANT_MAX_EVENTS_PER_SECOND` Realtime ke 20.000 lewat `docker/compose.loadtest.yml` (opt-in), lalu dikembalikan. Sudah diverifikasi: tenant kembali 1.000.
- **Tanpa push nyata.** User uji `lt_*` tidak punya perangkat push. Notifier dihentikan selama uji beban dan dinyalakan lagi. `push_queue` 4 baris sebelum dan sesudah uji. Kanal alert Telegram/email nonaktif di dev, jadi tidak ada pesan alert keluar. Tidak ada sistem eksternal yang dihubungi, dan tidak ada laporan yang dibuat.
- **Waktu uji:** malam WIB, di luar jam ramai 08:55–09:30. Slow mode otomatis jam ramai (10 dtk per user di room saham) tidak aktif.

### 3.2 Konfigurasi edge produksi

**Statis** (`static-config.tsv`): 84 ok, 0 temuan, 8 catatan.

- Semua router `websecure` di `prod.yml` memakai `Host(PROXY_DOMAIN)` dan tidak membuka `/auth/v1`, `/pg`, `/graphql/v1`, Studio, `/api/mcp`, atau `PathPrefix(/)`.
- Entrypoint admin hanya di `127.0.0.1`. HTTP dialihkan ke HTTPS.
- TLS ≥ 1.2, `sniStrict` default `true`, cipher hanya ECDHE+AEAD, kurva X25519/P-256/P-384.
- HSTS 1 tahun + includeSubdomains, CSP API `default-src 'none'`, `frameDeny`, nosniff, header `Server` dihapus.
- Batas body di semua router non-WebSocket. Akses log membuang header.
- CORS produksi default kosong (menjadi origin `cors-disabled.invalid`), dev `*`. Web CS produksi satu origin dengan `ipAllowList` VPN.
- Kong hanya mempercayai `X-Forwarded-For` dari subnet edge. Traefik tidak mempercayai `X-Forwarded-For` klien; terbukti lewat probe: header palsu lewat Traefik tidak mengubah IP yang dilihat auth-bridge.

Catatan:

- `/functions/v1` dan `cs_api` publik (T4, T10).
- `/realtime/v1/api/*` publik: `tenants`/`openapi` diblok Kong.
- Rate limit `depth: 0` (T3).
- HSTS tanpa preload, tanpa Permissions-Policy.
- `TRUSTED_PROXIES` auth-bridge mencakup semua RFC 1918.

## 7. Rekomendasi

### 7.1 Realtime untuk room ramai (T1, T2), prioritas sebelum produksi

1. **Ganti pengiriman pesan room dari `postgres_changes` ke Broadcast dari database.**
   - Pakai trigger `realtime.send`/`realtime.broadcast_changes` ke topik baca-saja `roomsys:<id>`, yang sekaligus menutup T2.
   - Otorisasi Broadcast dicek sekali saat join, bukan RLS per pesan per penerima, sehingga beban DB tidak tumbuh dengan jumlah penerima.
   - Pola ini sudah dipakai untuk tanda terima (0018) dan tiket CS.
2. **Naikkan `REALTIME_MAX_EVENTS_PER_SECOND`** (env compose; tenant di-seed ulang dari env saat start), mis. 5.000. Jadikan `MessagePerSecondRateLimitReached` alert sentinel.
3. **Klien:** isi celah pesan berkala (`get_messages(p_after)` tiap 15–30 dtk saat room terbuka), bukan hanya saat tersambung ulang. Event yang dibuang batas tenant tidak memberi sinyal ke klien.
4. **Produk:** slow mode jam ramai menekan pesan per user, tetapi tidak menekan fan-out. N pengirim aktif dengan slow mode 10 dtk menghasilkan ≈ N²/10 event/dtk, jadi 100 pengirim aktif sudah 1.000 event/dtk. Pertimbangkan:
   - batas penerima live per room, sisanya mendapat sampling/ringkasan;
   - room per sesi.

### 9.1 Perubahan alat ukur

### 9.3 Bottleneck pertama yang baru (±450–500 penerima di satu room)

Dua batas tercapai hampir bersamaan. Keduanya baru muncul jauh di atas titik gagal sebelumnya (±150 penerima).

**1. Batas tenant 10.000 event/dtk (konfigurasi)**

- Fan-out satu room = pesan/dtk × penerima ≈ N²/20 pada skenario ini, sehingga 10.000/dtk tercapai di ±450 penerima.
- Pada 600 VU (±18.000 event/dtk diminta), log Realtime menunjukkan `MessagePerSecondRateLimitReached` lalu 456 × `UnableToBroadcastChanges: :too_many_requests` (16:41 dan 16:45). Pesan yang dibuang tidak memberi sinyal ke klien.
- Gap-fill hanya mengambil `pesan terbaru − 3 dtk`. Karena pesan sesudahnya tetap sampai, lubang di tengah aliran **tidak** tertambal: hanya 1.335 dari ±93 ribu pesan yang hilang didapat lewat gap-fill (9.6).

**2. Konvoi kunci baris `chat_rooms` + pool PostgREST (perangkat lunak)**

Mekanismenya:

- Setiap pesan meng-update baris yang sama, `chat_rooms` (`last_message_at`/`preview`, trigger `messages_after_insert`). Kunci baris itu dipegang sampai PostgREST mengirim `COMMIT`.
- Pada ±25–30 pesan/dtk ke satu room, terjadi lonjakan:
  - `pg_stat_activity` dipenuhi `send_message` yang menunggu `Lock:transactionid`, di belakang transaksi `idle in transaction (ClientRead)` yang menunggu PostgREST;
  - pool PostgREST (10) habis, lalu `PGRST003 Timed out acquiring connection` (504);
  - CPU `rest` melompat dari ±8% ke 100% dan tetap di sana.
- Ini kegagalan metastabil, bukan beban yang naik bertahap.

### 12.8 T25: job trending harian bentrok dengan tick (4 Nov)

**Penyebab:** `social-trending-rebuild` dijadwalkan `40 2 * * *`, dan menit 40 juga dijalankan `social-trending` (`*/5 * * * *`). Keduanya memanggil `private.trending_refresh`, yang menghapus agregat sejak waktu awal lalu mengisinya ulang. Pada 4 Nov 02:40:00 UTC tick berjalan .012–.023 dan rebuild mulai .018; rebuild gagal `duplicate key value violates unique constraint "stock_mention_buckets_pkey"` (bucket `LTPOST` 02:35, dari postingan uji beban). Stack berjalan sejak 3 Nov, jadi rebuild harian baru sekali dicoba dan gagal; alert `cron:social-trending-rebuild` terbuka sejak itu.

**Dampak:** trending tetap dihitung tiap 5 menit. Yang tidak jalan: koreksi agregat 15 hari dan pembersihan agregat lebih tua dari `trending.bucket_retention_days` (35 hari), sehingga tabel terus tumbuh.

**Perbaikan** (`0111_trending_job_lock`): `private.trending_tick` dan `private.trending_rebuild` mengambil `pg_advisory_xact_lock(hashtext('private.trending'))` sebelum `trending_refresh` (pemanggilan dipindah dari `declare` ke badan fungsi). Job yang datang belakangan menunggu yang pertama commit, lalu bekerja dengan snapshot baru. Jadwal tidak diubah.

**Verifikasi:**

- Sesi A: `begin; trending_tick(); pg_sleep(5); commit`. Sesi B memanggil `trending_rebuild()` 1,5 dtk kemudian: B selesai 9 ms setelah A commit (menunggu kunci), tanpa error.
- `test-db` **91 file / 2.738 tes PASS**: baru `091_trending_job_lock_test.sql` (6 tes: kunci dipegang sampai akhir transaksi, rebuild sesudah tick tidak bentrok, jadwal tidak berubah).
- Alert `cron:social-trending-rebuild` selesai setelah rebuild terjadwal berikutnya berhasil (02:40 UTC).

**Catatan CPU db 12.7:** konfigurasi Postgres image 17.6.1.136 dan 17.11.0.008 identik (`shared_buffers` 128 MB, `effective_cache_size` 128 MB, JIT `llvmjit` aktif). CPU puncak db pada 600 penerima sebelumnya juga berkisar 70–109% antar putaran (11.3), jadi 99% masih dalam rentang itu dan latensi membaik. Bukan regresi. Pada 600 penerima aktif db mendekati batas 2 vCPU; produksi memakai 4 vCPU (`docs/dev-server.md`, `PRODUCTION.md`). `room_preview_worker` paling besar di `pg_stat_statements` karena desainnya (±9 dtk per panggilan, sebagian besar `pg_sleep(1)`), bukan CPU.
